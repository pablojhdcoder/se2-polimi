\section{Data Layer Integration}
\label{sec:data_layer_integration}%

This section describes the integration plan for the data layer components of the Best Bike Paths system, including the relational database (PostgreSQL), repository abstractions, migrations, and the cache layer (Redis). The data layer forms Level 1 of the integration strategy (see \Cref{sec:integration_levels}) and must be validated before service-layer integration.

\subsection{DBMS Integration}
\label{subsec:dbms_integration}%

The system uses \textbf{PostgreSQL} as the primary DBMS for persistent storage of users, trips, paths, ratings, and related entities, as defined in the Design Document (DD). Integration testing for the PostgreSQL database covers the following aspects.

\textbf{Database schema validation.} Tests verify that the deployed schema matches the expected entity-relationship model: tables for users, trips, paths, path segments, ratings, reviews, and supporting entities; correct primary and foreign key constraints; indexes on frequently queried columns (e.g., path identifiers, user identifiers, timestamps); and check constraints for data validity (e.g., rating values in a defined range).

\textbf{Migration testing.} Integration tests run database migrations (e.g., Flyway or equivalent) against a test database and assert that: migrations apply successfully in order; rollback (when supported) restores the previous state; and seed or reference data required for tests is loaded correctly. This ensures that the same migration set used in development and production can be applied reliably in test environments.

\textbf{Repository integration with database.} Each repository (User, Trip, Path, Rating, etc.) is tested against a real PostgreSQL instance (or a containerised one) rather than mocks. Tests cover create, read, update, and delete operations; queries with filters and pagination; and correct mapping between domain entities and database rows. Connection pooling and configuration (e.g., via environment variables) are validated.

\textbf{Transaction management.} Tests assert that multi-step operations execute within transactions where required: successful commits persist all changes; failures trigger rollback so that partial updates do not leave the database in an inconsistent state; and isolation behaviour is as expected for concurrent access scenarios relevant to the application.

\textbf{Data integrity constraints.} Integration tests deliberately violate unique constraints, foreign key constraints, and not-null constraints to ensure that the DBMS and the application layer reject invalid data appropriately and that error handling and reporting are consistent.

\subsection{Cache Layer Integration}
\label{subsec:cache_layer_integration}%

The system uses \textbf{Redis} as a cache layer to reduce load on PostgreSQL and to store session-related or frequently accessed data (e.g., path search results, user session tokens), as described in the DD. Integration testing for the Redis cache includes the following.

\textbf{Cache configuration and connection.} Tests verify that the application connects to Redis using the configured host, port, and credentials (if any); that connection failures are handled gracefully (e.g., fallback to DB or clear error); and that reconnection behaviour works after temporary network or Redis outages.

\textbf{Cache hit and miss scenarios.} Tests populate the cache with known keys and values, then request those keys (expecting hits) and request keys that do not exist (expecting misses). The application behaviour is validated in both cases: correct data returned on hit, and correct fallback to the database or computation on miss, with optional cache population for subsequent requests.

\textbf{TTL (Time To Live) policies.} Tests set entries with a defined TTL and assert that after the TTL expires, the key is no longer returned (or is evicted). This ensures that cached data does not become stale beyond the intended lifetime (e.g., for path search results or session data).

\textbf{Cache eviction strategies.} When Redis is configured with a maximum memory policy (e.g., volatile-lru), tests verify that under memory pressure the expected eviction behaviour occurs and that the application still behaves correctly when previously cached entries are evicted (e.g., by refetching from the database).

\textbf{Cache invalidation on data updates.} When the application updates or deletes data in PostgreSQL (e.g., path published, user updated), integration tests assert that the corresponding cache entries are invalidated or updated so that subsequent reads do not serve stale data. This validates the consistency between cache and database for the tested update flows.

\section{Service Layer Integration}
\label{sec:service_layer_integration}%

This section describes the integration plan for all microservices in the system.

\subsection{User Management Service Integration}
\label{subsec:user_management_service_integration}%

The User Management Service is responsible for registration, login, profile management, and password recovery, supporting use cases such as UC1 (User Registration) and UC2 (Login) from the RASD. Integration testing for this service covers the following.

\textbf{Service-to-DB integration.} The service uses a User repository to persist and retrieve user entities in PostgreSQL. Integration tests verify that: user registration creates a correct record (e.g., email, hashed password, profile fields) and respects unique constraints on email; login queries the database and validates credentials; profile updates and password changes are persisted within transactions; and duplicate registration attempts are rejected with appropriate errors. Repository methods are exercised against a real or containerised database as in \Cref{subsec:dbms_integration}.

\textbf{Integration with Email Service for verification and recovery.} When the system supports email verification or password reset, integration tests validate that the User Management Service invokes the Email Service (or a test double with contract verification) with the expected parameters (e.g., recipient, template, token link). Tests cover both success and failure paths (e.g., email send failure) and ensure that user state (e.g., verification flag, reset token) is updated consistently.

\textbf{Authentication and authorization flows.} Tests verify that login returns a valid token or session identifier that is accepted by the API Gateway or other services; that invalid or expired tokens are rejected; and that protected endpoints correctly enforce authorization (e.g., a user can access only their own profile). Integration with the API Gateway's authentication middleware is tested at the boundary where the service validates credentials and issues tokens.

\textbf{Password hashing and validation.} Integration tests ensure that passwords are never stored in plain text; that a standard secure hashing algorithm (e.g., bcrypt or Argon2) is used; that login correctly validates the user-supplied password against the stored hash; and that password policy checks (if any) are applied before persistence. This validates the security-related behaviour of the service in an integrated environment.

\subsection{Trip Management Service Integration}
\label{subsec:trip_management_service_integration}%

The Trip Management Service handles the creation, update, and retrieval of personal trips (e.g., UC8: Record Personal Trip, UC10: View Trip Statistics from the RASD). Integration testing for this service covers the following.

\textbf{Service-to-DB integration.} The service uses a Trip repository (and related entities such as trip segments or waypoints) to persist trip data in PostgreSQL. Integration tests verify that: creating a trip stores the correct user association, timestamps, and optional metadata; updating a trip (e.g., end time, computed statistics) persists correctly; queries by user and date range return the expected trips; and deletion or soft-delete behaviour is consistent. Transactions are used where multiple entities are written (e.g., trip header and segments).

\textbf{Integration with Sensor Data Processing Service.} When trips are created or updated using data from the Sensor Data Processing Service (e.g., GPS points, aggregated statistics), integration tests validate that the Trip Management Service correctly consumes the data provided (via API or message queue) and maps it into trip entities and segments. Tests cover success and failure responses (e.g., invalid or incomplete sensor data) and ensure that trip state remains consistent.

\textbf{Integration with Weather API.} If trip metadata includes weather conditions at the time of the trip, integration tests verify that the Trip Management Service requests weather data (from the Weather API or a test double) with the correct parameters (e.g., location, timestamp) and stores or associates the result with the trip. Fallback behaviour when the Weather API is unavailable should be tested (e.g., store null or default, or retry according to policy).

\textbf{Trip data validation and storage.} Tests assert that invalid inputs (e.g., missing user, invalid timestamps, malformed segments) are rejected before persistence; that computed fields (e.g., duration, distance) are correctly derived and stored; and that the service respects business rules (e.g., a trip cannot end before it starts). This ensures data quality and consistency at the service boundary.

\subsection{Sensor Data Processing Service Integration}
\label{subsec:sensor_data_processing_service_integration}%

The Sensor Data Processing Service is responsible for consuming raw sensor data from the mobile client (via the Message Queue), validating and processing it, and persisting the resulting path or trip data. Integration testing must verify that the service correctly integrates with RabbitMQ, the database, and downstream consumers.

\textbf{Message Queue (RabbitMQ) integration.}
The service subscribes to one or more queues where the client (or Trip Detection Engine) publishes GPS and sensor payloads. Tests must ensure: (a) the service connects to RabbitMQ with the configured credentials and virtual host; (b) messages are consumed in order (or with explicit ordering guarantees where required); (c) malformed or empty messages are rejected or logged without crashing the consumer; (d) acknowledgment (ACK) and negative acknowledgment (NACK) behaviour is correct so that failed processing does not lose messages or block the queue indefinitely.

\textbf{Service-to-DB integration.}
Processed sensor data is written to the database (e.g. path points, trip segments). Integration tests must validate: schema compliance (coordinates, timestamps, user/trip identifiers), transaction boundaries (all-or-nothing for a batch of points), and consistency with the Path Management and Trip Management services' expectations (foreign keys, constraints).

\textbf{GPS data processing and outlier removal.}
The service may apply filtering (e.g. outlier removal, smoothing). Tests must verify that invalid or physically implausible points (e.g. sudden jumps) are either corrected or discarded, and that the resulting trajectory is consistent with business rules (e.g. max speed, minimum sampling interval).

\textbf{Obstacle detection validation.}
If the service receives or produces obstacle-related events, integration tests must ensure that obstacle reports are correctly parsed, validated, and either stored or forwarded to the Path Management Service (or other subscribers) with the expected format and semantics.

Integration testing for the Sensor Data Processing Service therefore includes:
\begin{itemize}
    \item Integration with Message Queue (RabbitMQ): connection, consumption, ACK/NACK, error handling
    \item Service-to-DB integration: writes, transactions, constraints
    \item GPS data processing and outlier removal: filtering logic and output consistency
    \item Obstacle detection validation: parsing, storage or forwarding of obstacle events
\end{itemize}

\subsection{Rating Service Integration}
\label{subsec:rating_service_integration}%

The Rating Service manages reviews and ratings for paths (e.g. user-submitted scores and comments). It must integrate with the Path Management Service to resolve path identities and with the database to persist and retrieve ratings. Integration testing must ensure correct data flow and business rules.

\textbf{Integration with Path Management Service.}
The Rating Service needs to validate that rated entities (paths) exist and to possibly expose aggregated ratings back to Path Management or Path Search. Tests must verify: (a) resolution of path IDs and handling of non-existent paths (e.g. 404 or validation error); (b) consistency of path metadata when ratings are displayed or aggregated; (c) no orphaned ratings when paths are deprecated or removed (e.g. soft-delete or cascade behaviour).

\textbf{Service-to-DB integration.}
Ratings are persisted in the database. Integration tests must validate: schema compliance (user ID, path ID, score, comment, timestamps), uniqueness constraints (e.g. one rating per user per path or per trip), and transaction behaviour when creating or updating ratings.

\textbf{Rating calculation and aggregation.}
The service may compute aggregates (e.g. average score, count) for display or for use by Path Search. Tests must verify that aggregates are correct after insert/update/delete, and that concurrent updates do not produce inconsistent values (e.g. use of appropriate isolation or locking).

\textbf{Rating validation and constraints.}
Business rules (e.g. score range 1--5, mandatory comment length, forbidden content) must be enforced at the service boundary. Integration tests must confirm that invalid inputs are rejected with appropriate error responses and that valid inputs are accepted and stored correctly.

Integration testing for the Rating Service therefore includes:
\begin{itemize}
    \item Integration with Path Management Service: path resolution, aggregate exposure, lifecycle handling
    \item Service-to-DB integration: persistence, constraints, transactions
    \item Rating calculation and aggregation: correctness and consistency under concurrency
    \item Rating validation and constraints: input validation and error handling
\end{itemize}

\section{API Gateway Integration}
\label{sec:api_gateway_integration}%

The API Gateway is the single entry point for client requests to backend services. It is responsible for routing, authentication, validation, and consistent response formatting. Integration testing must verify that the gateway correctly forwards requests to the appropriate microservices and applies cross-cutting concerns.

\textbf{Request routing to appropriate services.}
Each API path (e.g. \texttt{/users}, \texttt{/paths}, \texttt{/ratings}) must be mapped to the correct backend service. Integration tests must send requests to the gateway and assert that the intended service receives the request (e.g. via logging, stub responses, or network inspection). Tests must cover path prefixes, path parameters, and query strings, and confirm that 404 is returned for unknown routes.

\textbf{API versioning.}
If the API supports versioning (e.g. \texttt{/v1/paths}, header \texttt{Accept-Version}), tests must verify that the correct version of each service is invoked and that deprecated or invalid versions are handled with clear error responses.

\textbf{Authentication and authorization middleware.}
The gateway must validate tokens or sessions and enforce authorization (e.g. only authenticated users can post reviews). Integration tests must verify: (a) unauthenticated requests to protected routes return 401; (b) valid tokens result in forwarded requests with user context; (c) forbidden actions return 403; (d) token expiry and refresh behaviour is correct.

\textbf{Request validation.}
Payload size limits, required headers, and basic schema validation (e.g. JSON structure) should be enforced at the gateway where applicable. Tests must confirm that invalid or oversized requests are rejected with 400 (or 413) and that valid requests reach the backend unchanged.

\textbf{Response formatting.}
The gateway may normalize response format (e.g. envelope, error shape). Integration tests must verify that successful and error responses from backend services are transformed into the agreed client contract (status codes, body structure).

\textbf{Error handling and status codes.}
When a backend service is unavailable or returns an error, the gateway must return appropriate status codes (e.g. 502, 503) and optionally retry or circuit-break. Tests must simulate backend failures and assert correct status codes and error payloads.

Integration testing for the API Gateway therefore includes:
\begin{itemize}
    \item Request routing to appropriate services: path mapping and 404 handling
    \item API versioning: version selection and deprecation handling
    \item Authentication and authorization middleware: 401/403, token forwarding, expiry
    \item Request validation: size, headers, schema, 400/413
    \item Response formatting: envelope and error shape consistency
    \item Error handling and status codes: 502/503, retries, circuit breaker
\end{itemize}

\section{External Services Integration}
\label{sec:external_services_integration}%

The system integrates with external third-party services for weather, maps, and email. Integration testing must verify connectivity, data handling, and resilience (timeouts, errors, fallbacks) without depending on live external availability in every run; use of stubs, mocks, or test harnesses is recommended.

\subsection{Weather API Integration}
\label{subsec:weather_api_integration}%

The Weather API provides current or forecast weather data for path or trip display (e.g. conditions along a route). Integration tests must cover:

\textbf{API connection and authentication.}
The backend must connect to the provider (e.g. OpenWeatherMap, custom API) using configured base URL and API key (or OAuth). Tests must verify that valid credentials yield a successful connection and that invalid or missing credentials yield a clear failure (e.g. 401 or connection error) without exposing secrets.

\textbf{Weather data retrieval.}
Requests with valid coordinates or location IDs must return weather data in the expected structure. Tests must assert that the response is parsed correctly (temperature, conditions, timestamps) and that the internal representation used by the application (e.g. Trip Management, Path Search) is consistent.

\textbf{Error handling and fallback mechanisms.}
When the external API is unavailable (timeout, 5xx), rate-limited (429), or returns invalid data, the application must handle the error gracefully (e.g. cache last known data, show a neutral state, or return a controlled error to the client). Integration tests must simulate these failures and verify the chosen fallback or error response.

\textbf{Data format validation.}
Unexpected or changed response formats from the provider must be detected (e.g. schema validation or sanity checks). Tests must feed malformed responses and assert that the application does not crash and either falls back or returns a clear error.

\subsection{Map Service API Integration}
\label{subsec:map_service_api_integration}%

The Map Service API provides map tiles, geocoding, or route visualization. Integration tests must cover:

\textbf{API connection and authentication.}
Connection to the map provider (e.g. provider-specific REST API, API key or token) must be verified. Tests must confirm that valid configuration allows successful calls and that authentication failures are handled without leaking credentials.

\textbf{Map data retrieval.}
Requests for tiles, bounds, or geocoding must return data in the expected format. Integration tests must verify that responses are correctly parsed and that coordinates and zoom levels are consistent with the application's expectations (e.g. for path overlay).

\textbf{Route visualization.}
If the application requests route geometry or rendering data from the map service, tests must verify that request parameters (waypoints, options) are correctly built and that the returned geometry or URLs are usable by the client (e.g. path drawing, static map images).

\textbf{Error handling and fallback mechanisms.}
Timeouts, quota exceeded, or invalid responses must be handled (e.g. fallback to cached tiles, or degrade to a simple map view). Integration tests must simulate failures and assert the defined fallback or error behaviour.

\subsection{Email Service Integration}
\label{subsec:email_service_integration}%

The Email Service sends transactional emails (e.g. verification, password reset, notifications) via SMTP or a provider API. Integration tests must cover:

\textbf{SMTP configuration.}
Connection to the SMTP server (host, port, TLS, credentials) must be validated. Tests must verify that valid configuration results in a successful connection and that invalid configuration (wrong host, bad credentials) fails with a clear error and does not expose secrets.

\textbf{Email sending functionality.}
Sending a well-formed email (to, subject, body) must result in the message being accepted by the SMTP server (or provider). Integration tests may use a test SMTP server or mock to assert that the correct recipient, subject, and body (or MIME parts) are sent.

\textbf{Email template rendering.}
Templates (e.g. verification link, reset token) must be rendered with the correct variables and escaping. Tests must supply representative data and verify that the rendered content is correct and that sensitive data (e.g. tokens) is present only where intended.

\textbf{Error handling and retry mechanisms.}
Transient failures (e.g. network error, 4xx/5xx from provider) must trigger retries or queueing according to policy. Integration tests must simulate failures and verify retry count, backoff, and final failure handling (e.g. dead-letter or alert).

\section{Client Integration}
\label{sec:client_integration}%

This section describes the integration plan for the mobile application components.

\subsection{Mobile Application Core Integration}
\label{subsec:mobile_application_core_integration}%

The Mobile Application Core (React Native with Expo) is the entry point for the user and coordinates the UI, the Client API layer, and local persistence. Integration testing for this component must verify that the UI module, the Client API, and local storage work together correctly and that navigation and routing behave as specified in the DD and RASD.

\textbf{User Interface Module integration.}
The UI is built from screens and components that consume application state and trigger actions (e.g., login, path search, trip recording). Integration tests must verify that: (a) each main screen renders without errors when supplied with valid props or mock state; (b) user actions (button presses, form submissions) invoke the correct handlers (e.g., Client API calls or navigation); (c) loading and error states are displayed consistently (e.g., spinners, error messages); and (d) navigation between screens (e.g., login $\to$ home $\to$ path list) follows the defined flow and preserves required context (e.g., authentication token). Tests may use a test renderer (e.g., React Native Testing Library) with mocked Client API and navigation.

\textbf{Client API integration.}
The Client API layer (e.g., \texttt{api.js}) is responsible for all HTTP communication with the backend via the API Gateway. Integration tests must verify that: (a) the base URL and headers (e.g., \texttt{Authorization} with Bearer token) are set correctly from configuration or environment; (b) each API method (e.g., login, get paths, post review, submit trip) builds the correct request (method, path, body) and parses the response (JSON, status codes); (c) successful responses are mapped to the format expected by the UI or other modules; and (d) errors (4xx, 5xx, network failure) are handled and surfaced (e.g., error callbacks or thrown exceptions) so the UI can show appropriate feedback. Tests should run against a real or containerised API Gateway/backend, or against a contract-compliant mock.

\textbf{Local Storage integration.}
The application uses local storage (e.g., AsyncStorage or equivalent) for session persistence (e.g., token, user ID), offline data, and preferences. Integration tests must verify that: (a) after login, the token and user identifiers are stored and can be read on next launch; (b) the Client API (or auth middleware) correctly attaches the stored token to outgoing requests; (c) logout or session expiry clears the relevant keys; and (d) read/write operations are consistent (e.g., no race conditions when multiple modules access storage). Tests may use an in-memory or test-specific storage implementation to avoid side effects.

\textbf{Navigation and routing.}
Navigation (e.g., React Navigation) must reflect the application's flow: unauthenticated users are directed to login/registration; authenticated users can reach home, path search, trip recording, and profile. Integration tests must verify that: (a) deep links or initial routes resolve to the correct screen; (b) back navigation and stack reset behave as expected; and (c) route parameters (e.g., path ID) are passed and available to the target screen. This ensures that the Mobile Application Core correctly integrates UI, API, and storage with the navigation layer.

Integration testing for the Mobile Application Core therefore includes:
\begin{itemize}
    \item User Interface Module integration: screen rendering, user actions, loading/error states, navigation flow
    \item Client API integration: base URL, headers, request/response handling, error handling
    \item Local Storage integration: token and user persistence, attachment to API, logout/clear
    \item Navigation and routing: initial route, authenticated vs.\ unauthenticated flow, route parameters
\end{itemize}

\subsection{Trip Detection Engine Integration}
\label{subsec:trip_detection_engine_integration}%

The Trip Detection Engine uses sensor data (GPS, accelerometer, gyroscope) to automatically detect when the user starts and stops a trip (e.g., cycling), supporting use cases such as UC8 (Record Personal Trip) from the RASD. Integration testing must verify that the engine correctly integrates with the Sensor Manager and the Client API, and that the detection algorithms and start/stop logic behave as specified.

\textbf{Integration with Sensor Manager.}
The Trip Detection Engine subscribes to GPS and motion sensors via the Sensor Manager. Integration tests must verify that: (a) when the engine is started, it registers with the Sensor Manager and receives location and motion updates; (b) the engine uses the received data (coordinates, speed, acceleration) as input to its detection logic; (c) when the engine is stopped, it unsubscribes from the Sensor Manager so that no orphan subscriptions remain; and (d) if the Sensor Manager reports an error (e.g., GPS unavailable), the engine handles it gracefully (e.g., pauses detection or notifies the UI) without crashing.

\textbf{Integration with Client API.}
When a trip is detected (start and stop), the engine (or a coordinating module) must send trip data to the backend (e.g., via the Client API or via a message queue). Integration tests must verify that: (a) at trip end, the engine (or app) builds the trip payload (e.g., start time, end time, GPS points, optional statistics) and invokes the correct API endpoint or publish function; (b) the payload format matches the backend contract (e.g., JSON schema); (c) success and failure responses (e.g., 201 vs.\ 4xx/5xx) are handled and reflected in the UI or local state; and (d) offline or queued submission (if supported) is tested so that trips are not lost when the network is temporarily unavailable.

\textbf{Trip detection algorithms.}
The engine applies heuristics or algorithms to distinguish trip motion from stationary or non-cycling motion. Integration tests must verify that: (a) when the device is stationary, the engine does not trigger a trip start; (b) when motion consistent with cycling (e.g., speed and pattern) is detected, the engine triggers trip start within an acceptable delay; (c) when motion stops for a sustained period, the engine triggers trip end; and (d) edge cases (e.g., brief stops at traffic lights, GPS drift) are handled so that false starts or merged trips are minimised. Tests may use recorded or synthetic sensor streams to achieve reproducible behaviour.

\textbf{Automatic trip start/stop detection.}
End-to-end integration tests must verify that: (a) from a standing start, simulated or real motion leads to a trip start event and, after motion stops, to a trip end event; (b) the resulting trip (start time, end time, trajectory) is consistent with the sensor data; and (c) the user (or UI) can optionally override (e.g., manual start/stop) and the engine respects that. This ensures that the Trip Detection Engine integrates correctly with the Sensor Manager and Client API and that automatic detection meets the product requirements.

Integration testing for the Trip Detection Engine therefore includes:
\begin{itemize}
    \item Integration with Sensor Manager: subscribe, consume data, unsubscribe, handle sensor errors
    \item Integration with Client API: build and send trip payload, handle response, offline/queue if applicable
    \item Trip detection algorithms: stationary vs.\ motion, start/stop triggers, edge cases
    \item Automatic trip start/stop detection: end-to-end flow from sensors to trip event and API
\end{itemize}

\subsection{Client-Server Integration}
\label{subsec:client_server_integration}%

The mobile application communicates with the backend through the API Gateway. Integration testing for client-server communication must validate the full request/response cycle, security, and resilience, as described in the DD Runtime View. The following aspects are covered.

\textbf{HTTPS communication.}
All client-server traffic must use HTTPS (TLS). Integration tests verify that: the client connects to the configured API base URL over TLS; certificate validation (or pinning, if used) is correctly applied; unencrypted HTTP requests to sensitive endpoints are rejected or redirected; and connection parameters (timeout, keep-alive) are consistent with the API contract. Tests may use a test server or proxy to assert that requests are sent over a secure channel.

\textbf{JSON request/response format.}
The API contract specifies JSON for request bodies and responses. Integration tests verify that: the client serializes payloads (e.g., registration data, path segments, search filters) into valid JSON with the expected structure and field names; the client correctly parses JSON responses (including nested objects and arrays) and maps them to the application model; malformed JSON from the server is handled without crashing (e.g., clear error or fallback); and content-type headers (\texttt{Application/JSON}) are sent and accepted. This ensures interoperability between the mobile client and the backend services behind the API Gateway.

\textbf{Session management.}
Authenticated flows require a token (e.g., JWT) or session identifier. Integration tests verify that: after login (UC2), the client stores the token securely (e.g., secure storage or keychain) and attaches it to subsequent requests (e.g., \texttt{Authorization} header); token expiry is detected and the user is prompted to re-authenticate or the client uses a refresh token if supported; logout or session invalidation clears the stored token and subsequent requests return 401; and concurrent sessions (if allowed) behave as specified. This validates the authentication lifecycle on the client-server boundary.

\textbf{Offline/online synchronization.}
The mobile app may operate offline (e.g., during a trip) and synchronize data when connectivity is restored. Integration tests verify that: the client detects connectivity loss and switches to offline mode (e.g., local storage, queueing of writes); when back online, queued operations (e.g., trip end, path points) are sent to the server in the correct order and with the expected payloads; conflicts (e.g., server-side updates) are handled according to the defined policy (e.g., last-write-wins or merge); and the user is informed of sync status or failures. Tests may simulate network loss and restoration to validate this behaviour.

\textbf{Error handling and retry mechanisms.}
Network failures, timeouts, and server errors (4xx, 5xx) must be handled gracefully. Integration tests verify that: transient failures (e.g., 503, connection timeout) trigger retries with backoff (if configured) and that the number of retries and backoff are as specified; non-retryable errors (e.g., 400, 401, 404) are not retried indefinitely and the user receives an appropriate message; the client does not crash on malformed or unexpected responses; and optional circuit-breaker or fallback behaviour (e.g., cached data) works when the server is repeatedly unavailable. This ensures robustness of the client-server integration under real-world conditions.

\section{End-to-End Integration}
\label{sec:end_to_end_integration}%

This section describes the integration plan for complete use case flows from the mobile client through the API Gateway and backend services to the database and external systems. E2E tests validate that the full stack works together as specified in the RASD and DD; they are executed after Levels 1--5 (\Cref{sec:integration_levels}) have been validated.

\subsection{Critical Use Cases}
\label{subsec:critical_use_cases}%

Critical use cases are those that must function correctly for the system to be usable: registration, login, manual path insertion, and path search/visualization. E2E integration testing covers the following.

\textbf{UC1: User Registration.}
The flow starts at the mobile client: the user enters email, password, and profile data; the client sends a \texttt{POST} request to the API Gateway (e.g., \texttt{/users/register}) with a JSON body. The gateway routes to the User Management Service, which validates input, hashes the password, and persists the user via the User repository to PostgreSQL. If email verification is required, the service may invoke the Email Service. E2E tests verify: end-to-end success (201, user stored in DB with hashed password); duplicate email returns 400/409 and no duplicate record; invalid payload (e.g., missing email) returns 400 and no persistence; and optional email delivery (or test double) when verification is enabled. The test runs with the real API Gateway, User Management Service, database, and (optionally) a test SMTP or mock.

\textbf{UC2: Login.}
The user enters credentials in the app; the client sends \texttt{POST} to the login endpoint with email and password. The API Gateway forwards to the User Management Service, which looks up the user in the database and validates the password; on success, it issues a token (e.g., JWT). E2E tests verify: valid credentials yield 200 and a token that is accepted on subsequent protected requests; invalid password or unknown email yield 401 and no token; token is correctly attached by the client for later API calls; and optional rate limiting or lockout behaviour after repeated failures. The full path Client $\to$ API Gateway $\to$ User Management $\to$ DB is exercised.

\textbf{UC3: Insert Path Information (Manual).}
The user creates a path manually by entering or drawing segments. The client sends path data (e.g., segments, metadata) to the API Gateway with a valid auth token; the gateway routes to the Path Management Service, which validates and persists the path (draft) in the database. E2E tests verify: authenticated user can create a path and receive 201 with path ID; path is stored with correct user association and status \emph{draft}; unauthenticated or invalid token returns 401; invalid payload (e.g., empty segments) returns 400; and the created path is retrievable (e.g., via UC9). Integration with the API Gateway, Path Management Service, and DB is validated.

\textbf{UC6: Search and Visualize Paths.}
The user searches for paths (e.g., by area, filters) and visualizes results on the map. The client sends a search request (e.g., \texttt{GET /paths?bbox=...}) to the API Gateway; the gateway routes to the Path Search Service, which may call the Path Management Service (or DB) to resolve path entities, apply scoring, and return a list. The client renders the results. E2E tests verify: valid search returns 200 and a list of paths (or empty list); results are consistent with published paths in the DB; filters (e.g., difficulty, length) are applied correctly; unauthenticated access (if allowed) or authenticated access works as specified; and map visualization receives correct geometry/data. The flow Client $\to$ API Gateway $\to$ Path Search $\to$ Path Management $\to$ DB is validated end-to-end.

\subsection{Advanced Use Cases}
\label{subsec:advanced_use_cases}%

Advanced use cases build on the critical ones and involve more components (sensors, message queue, external services, multiple services). E2E integration testing covers the following.

\textbf{UC4: Insert Path Information (Automated).}
Path data is collected automatically via sensors (GPS, etc.) and sent to the backend. The mobile client (Trip Detection Engine, Sensor Manager) publishes sensor payloads to RabbitMQ; the Sensor Data Processing Service consumes messages, processes them, and persists path/trip data via Path Management or Trip Management. E2E tests verify: from client publish to DB persistence, the full pipeline works; path/trip is created or updated with correct segments and user association; ordering and at-least-once delivery (or defined semantics) are respected; and failure in processing (e.g., invalid payload) is handled (e.g., NACK, no corrupt state). Client, Message Queue, Sensor Data Processing, Path/Trip Management, and DB are involved.

\textbf{UC5: Publish Path Information.}
The user publishes a draft path so it becomes visible in search. The client sends a publish request (e.g., \texttt{PATCH /paths/\{id\}} or \texttt{POST /paths/\{id\}/publish}) with valid token; the Path Management Service updates the path status to \emph{published}. E2E tests verify: owner can publish and path becomes visible in UC6 search; non-owner receives 403; invalid path ID returns 404; and published path is correctly returned by Path Search. API Gateway, Path Management, and DB are validated.

\textbf{UC7: Post Review.}
The user submits a rating and optional comment for a path. The client sends \texttt{POST} to the ratings endpoint with path ID, score, and comment; the API Gateway forwards to the Rating Service, which validates the path (e.g., via Path Management) and persists the rating in the DB. E2E tests verify: authenticated user can post a review and receive 201; rating is stored and linked to user and path; invalid path ID returns 404; duplicate rating (if one per user per path) returns 400/409; and aggregate (e.g., average) is updated for the path. Rating Service, Path Management, and DB are involved.

\textbf{UC8: Record Personal Trip.}
The user records a trip (start/stop or automatic detection). Trip data may be sent via API or message queue. The Trip Management Service (and optionally Sensor Data Processing) persists the trip and segments. E2E tests verify: trip is created and updated (e.g., end time, statistics) and stored with correct user association; trip is retrievable (UC10); and integration with sensor pipeline (if used) is correct. Trip Management, DB, and optionally RabbitMQ and Sensor Data Processing are validated.

\textbf{UC9: See Path Data.}
The user views detailed path data (e.g., segments, metadata). The client requests \texttt{GET /paths/\{id\}}; the API Gateway routes to Path Management (or Path Search), which returns the path. E2E tests verify: published path or own draft is returned with correct data; unauthorized access to another user's draft returns 403; 404 for non-existent path; and response format matches client expectations. Path Management and DB are validated.

\textbf{UC10: View Trip Statistics.}
The user views statistics for their trips. The client requests trip list or trip details (e.g., \texttt{GET /trips}); the Trip Management Service returns data from the DB. E2E tests verify: user receives only their trips with correct statistics (duration, distance, etc.); empty list for user with no trips; and 401 without valid token. Trip Management and DB are validated.

\textbf{UC11: Check Review.}
The user consults reviews for a path. The client requests \texttt{GET /paths/\{id\}/reviews} or similar; the Rating Service (or Path Management) returns ratings and comments. E2E tests verify: list of reviews is returned with correct path association; ordering and pagination work; and 404 for non-existent path. Rating Service, Path Management, and DB are validated.

\textbf{UC12: Merge Information from Multiple Users.}
The system merges path/segment data from multiple users (e.g., for a shared path). The Information Merging Service obtains data from Path Management (or DB), applies merge logic, and writes merged result back; the client may trigger or display the merged path. E2E tests verify: merge request results in a consistent merged path stored or exposed via Path Management; conflict resolution and freshness rules are applied; and the merged path is retrievable and visible where specified. Information Merging, Path Management, and DB are validated end-to-end.

\section{Service-to-Service Integration}
\label{sec:service_to_service_integration}%

Backend microservices interact both synchronously (REST) and asynchronously (message queue). Integration testing for service-to-service communication validates that services correctly invoke each other, handle failures, and respect contracts, as defined in the DD component and runtime views.

\textbf{REST API communication between services.}
Services call each other via HTTP/REST (e.g., Path Search calls Path Management to resolve path metadata; Rating Service calls Path Management to validate path IDs; Trip Management may call Weather API or internal Weather proxy). Integration tests verify that: the calling service sends correctly formed requests (URL, method, headers, body) according to the callee's API contract; the callee returns the expected status and body; response parsing and mapping in the caller are correct; and idempotent vs.\ non-idempotent operations are used appropriately. Tests run with real or contract-compliant stubs for the callee so that the full request/response flow is validated. Cross-service authorization (e.g., service-to-service tokens or internal network policies) is verified where applicable.

\textbf{Asynchronous communication via Message Queue.}
Sensor data and other events flow through RabbitMQ. The Sensor Data Processing Service consumes messages published by the client (or by other services); Trip Management or Path Management may consume or produce events. Integration tests verify that: producers publish messages with the expected format and routing (exchange, queue); consumers connect, subscribe, and process messages correctly; ACK is sent only after successful processing and NACK or requeue behaviour on failure is as specified; message ordering and at-least-once (or exactly-once) semantics are respected where required; and dead-letter or error queues are used when configured. Tests use a real or test RabbitMQ instance to validate the full async flow between services.

\textbf{Error handling between services.}
When a callee returns an error (4xx, 5xx) or is unavailable, the caller must handle it appropriately. Integration tests verify that: 4xx responses (e.g., 404 path not found) are handled without retrying indefinitely and that the caller returns a consistent error to its client or triggers fallback logic; 5xx or timeouts trigger retries (if configured) and eventually failure or circuit-breaker behaviour; partial failures (e.g., one of several parallel calls fails) do not leave the system in an inconsistent state; and errors are logged or propagated so that observability and debugging are possible. Simulating callee failures (e.g., mock returning 503) validates the caller's error handling.

\textbf{Service discovery and routing.}
In deployment, services resolve each other by name (e.g., DNS, Kubernetes service names) or via a discovery mechanism. Integration tests verify that: the calling service resolves the callee's endpoint correctly in the test environment (e.g., via config or discovery); routing reaches the intended service instance (no wrong target); and when multiple instances exist, load balancing or routing behaviour is as expected. This is especially important in containerised or orchestrated environments where service URLs are dynamic.

\textbf{Timeout and retry mechanisms.}
Calls between services should use configurable timeouts and retries to avoid cascading failures. Integration tests verify that: the caller applies a timeout and does not block indefinitely when the callee is slow or unresponsive; retry policy (max attempts, backoff) is applied for transient failures and not for permanent errors (e.g., 400); and that repeated failures (e.g., circuit breaker open) prevent overwhelming the callee and allow recovery. Tests simulate slow or failing callees to validate timeout and retry behaviour in the integrated system.

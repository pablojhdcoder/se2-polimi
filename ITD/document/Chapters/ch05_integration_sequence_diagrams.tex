\section{Backend Integration Sequences}
\label{sec:backend_integration_sequences}%

This section presents sequence diagrams illustrating integration flows for backend components.

\subsection{Service-to-DB Integration Sequences}
\label{subsec:service_to_db_sequences}%

Service-to-database integration follows a common pattern: a backend service (e.g., User Management, Trip Management, Path Management) receives a request, invokes the appropriate repository abstraction, and the repository executes SQL or ORM operations against PostgreSQL. Optionally, the service or repository interacts with the Redis cache for reads or invalidations. The sequences below illustrate these flows for the data layer and core services described in \Cref{sec:data_layer_integration} and \Cref{sec:service_layer_integration}.

\textbf{Generic read flow.} The client or API Gateway calls the service with a query (e.g., get user by ID, list trips by user). The service calls the repository method (e.g., \texttt{findById}, \texttt{findByUserId}). If a cache layer is used, the repository or a dedicated cache component checks Redis first; on a cache hit, the value is returned without querying the database. On a cache miss, the repository queries PostgreSQL, maps the result to a domain entity, optionally caches the result (with TTL), and returns it to the service, which then returns the response to the caller.

\textbf{Generic write flow.} For create, update, or delete operations, the service receives the request, validates input, and calls the repository (e.g., \texttt{save}, \texttt{update}, \texttt{delete}). The repository runs the operation within a transaction against PostgreSQL. On success, the transaction is committed; if a cache exists for the affected entity or query, the cache entry is invalidated or updated. The service returns the appropriate status and body to the caller. On failure (e.g., constraint violation), the transaction is rolled back and an error is returned.

\textbf{User Management example.} For user registration (UC1), the User Management Service receives the registration payload, calls the User repository to persist the user (with hashed password), and the repository performs an \texttt{INSERT} into the users table. For login (UC2), the service calls the repository to find the user by email; the repository queries PostgreSQL (and optionally the cache) and returns the user entity so the service can validate the password and issue a token.

\section{Client Integration Sequences}
\label{sec:client_integration_sequences}%

\subsection{Mobile Application Integration Sequences}
\label{subsec:mobile_application_sequences}%

The Mobile Application Core integrates the UI, the Client API layer, and local storage. Typical flows include: (a) login---user enters credentials, UI calls Client API, API returns token, token is stored and attached to subsequent requests; (b) path search---user triggers search, UI calls Client API (e.g.\ \texttt{GET /paths}), API Gateway and backend return results, UI renders the list; (c) navigation---after login, the app navigates to home and route parameters (e.g.\ path ID) are passed to detail screens. Integration tests and sequence diagrams must cover these flows and the interaction between UI, Client API, and local storage.

\textbf{Login and token persistence flow.} The user enters email and password; the UI invokes the Client API \texttt{login} method. The Client API sends \texttt{POST /auth/login} (or equivalent) to the API Gateway; the backend validates credentials and returns a token. The Client API parses the response and returns success to the UI; the UI (or a dedicated auth module) stores the token and user ID in local storage. On subsequent requests, the Client API reads the token from storage and attaches it to the \texttt{Authorization} header. \cref{fig:sequence_mobile_app} shows the login and token persistence flow. A standalone version of this diagram is available in \path{Images/Diagrams/Seq_Agent3_MobileApp.tex}.

\subsection{Sensor Integration Sequences}
\label{subsec:sensor_integration_sequences}%

The Sensor Manager is the single point of access for device sensors (GPS, accelerometer, gyroscope). The Trip Detection Engine and the Obstacle Detection Module subscribe to the Sensor Manager to receive location and motion data. Typical flows include: (a) start sensors---caller (e.g.\ Trip Detection) requests the Sensor Manager to start GPS and motion sensors; the manager checks permissions, starts platform-specific subscriptions, and delivers updates to registered listeners; (b) deliver updates---the Sensor Manager receives raw data from the platform and forwards it (with consistent format) to the Trip Detection Engine and Obstacle Detection Module; (c) stop and cleanup---when the caller stops, the manager unsubscribes and releases resources. Integration tests and sequence diagrams must cover these flows.

\textbf{Sensor subscription and data flow.} The Trip Detection Engine (or Obstacle Detection Module) calls the Sensor Manager to start GPS and accelerometer/gyroscope. The Sensor Manager checks runtime permissions; if granted, it starts the platform location and motion APIs and registers listeners. When the platform delivers location or motion events, the Sensor Manager normalises the data (e.g.\ coordinate system, units) and forwards it to all registered callbacks (Trip Detection, Obstacle Detection). When the engine or module stops, it calls the Sensor Manager to stop; the manager unsubscribes from the platform APIs and clears callbacks. \cref{fig:sequence_sensor_integration} shows the sensor subscription and data flow. \subsection{Client-Server Communication Sequences}
\label{subsec:client_server_sequences}%

Client-server communication flows cover the full path from the mobile client to the API Gateway and backend services. All traffic uses HTTPS; request and response bodies are JSON. The client attaches an authentication token (e.g., JWT) to protected requests after login (\Cref{subsec:mobile_application_sequences}).

\textbf{Authenticated API request flow.} The user triggers an action (e.g., search paths, create path). The mobile client builds the request (method, path, optional JSON body), reads the stored token from local storage, and sends an HTTPS request to the API Gateway with the \texttt{Authorization} header. The gateway validates the token, resolves the target service (e.g., Path Search, Path Management), and forwards the request. The backend service processes the request (e.g., queries the database), returns a response to the gateway, and the gateway returns the response to the client. The client parses the JSON response and updates the UI or local state. \Cref{fig:sequence_client_server} illustrates this flow. \subsection{Critical Use Case Sequences}
\label{subsec:critical_use_case_sequences}%

\textbf{UC1: User Registration.} The client sends \texttt{POST /users/register} with email, password, and profile data. The API Gateway routes to the User Management Service, which validates input, hashes the password, and calls the User repository to persist the user in PostgreSQL. Optionally, the service invokes the Email Service for verification. The response (201 + user or token) is returned along the chain. \Cref{fig:sequence_e2e_uc1} shows this flow.

\textbf{UC2: Login.} The client sends \texttt{POST /auth/login} with email and password. The gateway forwards to the User Management Service, which looks up the user in the DB and validates the password; on success it issues a token (e.g., JWT). The client stores the token and attaches it to subsequent requests. The sequence is similar to \Cref{fig:sequence_e2e_uc1} with login payload and token in the response.

\textbf{UC3: Insert Path Information (Manual).} The client sends path data (segments, metadata) with a valid token to the API Gateway; the gateway forwards to the Path Management Service, which validates and persists the path (draft) in the DB. The flow is Client $\to$ API Gateway $\to$ Path Management $\to$ DB; response 201 with path ID.

\subsection{Advanced Use Case Sequences}
\label{subsec:advanced_use_case_sequences}%

\textbf{UC4: Insert Path Information (Automated).} The client (or Trip Detection Engine) publishes sensor payloads to RabbitMQ; the Sensor Data Processing Service consumes messages, processes them, and persists path/trip data via Path Management or Trip Management. The E2E sequence is Client $\to$ RabbitMQ $\to$ Sensor Data Service $\to$ Path/Trip Management $\to$ DB (\Cref{subsec:message_queue_sequences}).

\textbf{UC5: Publish Path Information.} The client sends a publish request with valid token; the API Gateway forwards to the Path Management Service, which updates the path status to published. Flow: Client $\to$ API Gateway $\to$ Path Management $\to$ DB.

\textbf{UC7: Post Review.} The client sends \texttt{POST} to the ratings endpoint with path ID, score, and comment. The gateway forwards to the Rating Service, which validates the path (e.g., via Path Management) and persists the rating in the DB. Flow: Client $\to$ API Gateway $\to$ Rating Service $\to$ Path Management (resolve path) $\to$ DB (store rating).

\textbf{UC8: Record Personal Trip.} Trip data is sent via API or message queue; the Trip Management Service (and optionally Sensor Data Processing) persists the trip and segments. Flow: Client $\to$ API Gateway or RabbitMQ $\to$ Trip Management / Sensor Data $\to$ DB.

\textbf{UC9: See Path Data.} The client requests \texttt{GET /paths/\{id\}}; the gateway routes to Path Management, which returns the path from the DB. Flow: Client $\to$ API Gateway $\to$ Path Management $\to$ DB.

\textbf{UC10: View Trip Statistics.} The client requests \texttt{GET /trips}; the Trip Management Service returns trip data from the DB. Flow: Client $\to$ API Gateway $\to$ Trip Management $\to$ DB.

\textbf{UC11: Check Review.} The client requests reviews for a path; the Rating Service (or Path Management) returns ratings and comments. Flow: Client $\to$ API Gateway $\to$ Rating Service $\to$ DB.

\textbf{UC12: Merge Information from Multiple Users.} The Information Merging Service obtains path/segment data from Path Management, applies merge logic, and writes the merged result back; the client may trigger or display the merged path. Flow: Client or trigger $\to$ Information Merging $\to$ Path Management (read/write) $\to$ DB.
